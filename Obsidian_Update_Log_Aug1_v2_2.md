# TLCS Update Log: August 1, 2026

## 1. Webhook Payload JSON Compliance (Pine Script)
- **The Issue**: The `TLCS_Native_Oscillator.pine` script was generating plain text alert messages (`Alert : Bearish Hidden Divergence...`) rather than a structured JSON payload for its `alert()` call. 
- **The Consequence**: The Netlify backend (`process-webhook-background.js`) strictly requires a JSON format to extract the trigger, secret, and symbol. The backend fallback parser failed to extract critical fields and threw a `400 Bad Request`. However, because Netlify background functions (`*-background.js`) instantly return an `HTTP 202 Accepted` status before execution, TradingView erroneously logged the webhook as "Successfully delivered" (green tick), masking the silent failure. This caused live signals to never reach the Supabase database.
- **The Fix**: Rewrote the `alert()` logic in `TLCS_Native_Oscillator.pine` to explicitly construct the properly formatted `_divPay` JSON object, perfectly mirroring the robust implementation in `TLCS_Native_Divergence.pine`. Additionally added the missing `webhook_secret` input field to the script.

## 2. Dashboard Realtime Connection Hang (Supabase JS)
- **The Issue**: The web dashboard (`dashboard.html` and other pages) was perpetually stuck on the "CONNECTING..." state for its live performance feed. 
- **The Consequence**: The locally hosted `supabase-js-v2.min.js` file was fundamentally corrupted. It was an 86-byte file containing a CDN firewall policy rejection error (`Request to GET ... not allowed by policy`) instead of the actual JavaScript library code. As a result, `window.supabase` remained undefined, causing the frontend initialization (`window.sb()`) to return `null` and trap the `loadPerformanceSnapshot` function in an infinite retry loop.
- **The Fix**: Replaced the broken local `<script src="supabase-js-v2.min.js">` tag with the official unpkg CDN link (`https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2`) across all 11 HTML pages in the `TLCS_Website_Deploy` folder, fully restoring frontend realtime connectivity.

## 3. Real Entry Timestamp vs Active Limit Generation Time (v2.2.2)
- **The Issue**: The mobile UI displayed the Limit Generation Time in the `REAL ENTRY` top-right box, and the **Hold Duration** metric (e.g., `HELD: 34m`) artificially included the entire waiting time for the limit order to fill.
- **The Consequence**: Because the backend calculated Hold Duration based strictly on `created_at` (the Limit Generation Time), the hold duration was bloated by the wait time. Furthermore, for legacy trades without a precise recorded trigger time, the UI fell back to displaying the limit generation time on the trade card.
- **The Fix**: The Netlify webhook (`process-webhook-background.js`) was updated to correctly extract and save the exact millisecond a limit order fills as a dedicated `meta.real_entry_time` property in the DB JSONB payload. The backend's `holdMins` mathematical formula was rebuilt to subtract this precise `real_entry_time` instead of `created_at`. The frontend UI logic was already equipped to consume `real_entry_time`, meaning all newly generated active limit trades that execute will now properly display the exact trigger time and calculate a 100% accurate net hold duration.

## 4. GitHub Actions Crash: Missing Environment Secrets
- **The Issue**: Both the `generate-tearsheet` and `close_stale_trades` GitHub Action cron workflows were instantly failing (crashing in under 30 seconds with Exit Code 1).
- **The Consequence**: Because GitHub Actions run on entirely separate virtual machines from Netlify, the Python scripts were unable to locate the `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` environment variables. The scripts are hardcoded to execute a `sys.exit(1)` immediately if these credentials are not found, preventing any market close tear sheets or stale trade sweeps from occurring. 
- **The Fix**: The necessary Supabase connection credentials were explicitly added directly to the GitHub Repository Secrets (`Settings > Secrets and variables > Actions`) for both the `RemoteURL` (Main Architecture) and `TLCS_Website` repositories. This allows the ephemeral GitHub Action runners to securely inject the tokens into the Python runtime environment at execution.
